Phase IV · authored

Inference systems and economics

Read

  • "How To Scale Your Model," Part 7 "All About Transformer Inference" (scaling book) — prefill/decode arithmetic intensity, throughput and latency tricks, "Designing an Effective Inference Engine," quantization, Appendix D "Speculative Sampling." Rebuild closed-book the batch size where decode flips to compute-bound.
  • Kwon et al., "Efficient Memory Management for Large Language Model Serving with PagedAttention" (SOSP 2023, arXiv:2309.06180) — §3 (memory waste under contiguous allocation), §4 (PagedAttention, the block-table KV manager, scheduling and preemption), §6 (the 2–4× throughput result). Write the evidence brief on that 2–4×.
  • "How To Scale Your Model," Part 8 "Serving LLaMA 3-70B on TPUs" (applied inference) — memory sizing, the compute-bound batch threshold in bf16 versus int8, prefill handling, "Visualizing the Latency Throughput Tradeoff." Redo one worked problem with quantized weights, predicting the new batch threshold first.
  • CS336 Lecture 6 "Kernels, Triton," with the FlashAttention/Triton half of Assignment 2 (cs336.stanford.edu) — optional. The kernel level, where "memory movement dominates" becomes code you can profile.

Do

Two bookkeeping exercises, one sitting, no GPU. The waste ledger: sample 200 synthetic requests with mixed lengths (prompts 100–2,000 tokens, outputs 50–1,000, output lengths unknown in advance), compute total KV memory reserved under contiguous max-length preallocation versus 16-token paged blocks, and report the fraction of reserved memory holding actual token state. The batching simulator: Poisson arrivals over the same request mix, a fixed KV memory budget, two schedulers, static batching (requests admitted and retired as a group) against continuous batching (a finished sequence's slots free immediately). Measure throughput and tail latency, then double the variance of output lengths, predict which scheduler degrades, and run it.

Then price a deployment. A federal agency stands up a document-processing service on one open-weights model from the roster, and you owe them capacity and cost. Price three workload shapes on the same model and hardware: short chat (~500-token prompts, ~200-token outputs, interactive latency), long-context RAG (~30,000 tokens of retrieved records per request, ~500-token outputs, interactive latency), and overnight batch (the same document jobs, no latency target). For each shape give the binding constraint, the achievable batch size under a stated KV budget, prefill and decode priced separately, and $/token plus requests-per-hour-per-chip, with every assumption tabled.

Done when the budget's own arithmetic shows why the long-context shape dominates cost, so that a reader can point to the line where its per-request KV cache caps batch size below the compute-bound threshold while prefill flops scale with context; it names the two levers that cut that cost most, each tied to a specific term in that line; and a reader who accepts your assumptions can recompute all three $/token figures.

Skip if you can already take a model config, a chip spec sheet, and a workload description and produce a $/token estimate with the binding constraint named.

Phase IV closes here. Add the current-model dossier: pick one frontier model from the roster page and write its hardware-and-deployment snapshot, meaning accelerator, HBM and interconnect fabric, parallelism scheme, achieved utilization, rack power and cooling, and cost uncertainty. Tie every scale claim to a delivered system rather than a nominal accelerator count. The phase gate, on the gates page, defends the data, compute, hardware, and serving arithmetic of one frontier deployment as a single connected account.

Take away

  • Serving cost is a property of the workload, not just the model. Prefill is compute-bound, decode is memory-bound, and the KV cache decides how many requests share each weight-read. Prompt-to-output ratio, context length, concurrency, cache reuse, and the latency target set $/token; parameter count only sets the scale.
  • Parameter count is not a price. "A 70B model costs ten times a 7B model to serve" fails twice. The same model on the same hardware spans roughly a hundredfold range in per-token cost along the latency-throughput curve, and a long-context workload can make the smaller model the expensive one by drowning it in KV cache.
  • Paging was worth 2–4× throughput because contiguous allocation left real token state in as little as 20.4–38.2% of KV memory, and continuous batching recovers the rest at the scheduler without touching any model math.
  • Quantization and speculative decoding exploit the compute left idle by memory-bound decode. Quantization shrinks the bytes moved and can shift outputs; speculative sampling spends flops to bank several tokens per weight-read and provably preserves the target distribution.
  • The decision this bears on is how much serving capacity a deployment needs, and whether to build the infrastructure that follows. The venue is the state public utility commission, where utilities file data-center demand forecasts to justify new generation and transmission.
  • LBNL's congressionally mandated 2024 United States Data Center Energy Usage Report (December 2024), projecting data-center load doubling to tripling by 2028, is the standing reference. Every megawatt in those filings is tokens served times joules per token, so every one embeds assumptions about batching, quantization, workload shape, and utilization.
  • Efficiency cuts cost per token, and cheaper tokens have so far meant more tokens rather than less demand. Both halves belong in any forecast you defend, including the IFP report's figures.
Check yourself
  1. API price sheets charge several times less for input tokens than output tokens. Ground that ratio in this week's arithmetic.
  2. Contiguous max-length KV allocation wastes memory two ways: name both, say which PagedAttention eliminates outright, and then say what sits idle under static batching with mixed output lengths and why continuous batching recovers it.
  3. Quantization and speculative decoding both accelerate decode. One can change the model's output distribution and one provably doesn't. Which is which, and why does the memory-bound regime make both work?
  4. Same model, same chips: rank short chat, long-context RAG, and overnight batch by $/token, name each shape's binding constraint, and say which single workload parameter the ranking is most sensitive to.

Answers. (1) Prefill processes the whole prompt in parallel at high arithmetic intensity, compute-bound, one weight-read amortized over thousands of tokens. Decode streams the weights once per generated token, memory-bandwidth-bound, so each output token buys far more hardware time. The price ratio is the arithmetic-intensity gap, discounted by whatever batching claws back. (2) Internal waste: slots preallocated for the maximum possible output that the actual output never uses, plus reserved-for-future slots holding nothing yet. External fragmentation: gaps between differently sized contiguous allocations too small to serve a new request. Paged blocks eliminate external fragmentation outright and cap internal waste at less than one block per sequence. Under static batching, finished sequences' slots sit idle until the longest member of the batch completes; continuous batching admits a waiting request into freed slots at the next step, which is scheduling only, so it composes cleanly with paging. (3) Quantization changes the stored weights and KV representation, so logits shift and outputs can differ, a usually small quality risk traded for fewer bytes moved. Speculative sampling drafts tokens cheaply and verifies them under an acceptance rule that preserves the target distribution: same outputs statistically, faster wall clock, extra flops spent. Both pay off because memory-bound decode leaves compute idle. (4) Overnight batch is cheapest: no latency target, so batch size climbs to the compute-bound threshold. Short chat sits in the middle: small per-request KV allows respectable batching, but the latency target stops short of the threshold, so it is bandwidth-bound. Long-context RAG is most expensive: a ~30k-token KV cache per request caps the batch far below threshold, so decode is memory-capacity-bound while prefill flops scale with context. The ranking is most sensitive to context length, which moves both the KV cap and the prefill bill at once.
