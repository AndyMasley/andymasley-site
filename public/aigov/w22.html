Distributed training

Read

  • The Ultra-Scale Playbook (Hugging Face nanotron, playbook) — "First Steps: Training on one GPU" through "5D parallelism in a nutshell," plus Appendix A0 on collectives; skip "Diving in the GPUs" except Flash Attention. Rebuild the 5D table closed-book: what each parallelism shards, communicates, on which link.
  • CS336 Lectures 7 and 8, "Parallelism" (cs336.stanford.edu) — the same material taught live, with Lecture 5 "GPUs, TPUs" as background.
  • FlashAttention (Dao et al., 2022, arXiv:2205.14135) — tiling, exactness, memory complexity, benchmark methodology. Write the evidence brief: separate the kernel-level speedup claims from the end-to-end training claims.
  • ZeRO (Rajbhandari et al., 2019, arXiv:1910.02054) — optional. §3 "Where Did All the Memory Go?", the three partitioning stages, §7's communication analysis. Shut the paper and rebuild the memory-accounting table, one row per stage.
  • The Llama 3 Herd of Models, §3.3 (Meta, 2024, arXiv:2407.21783) — optional. §3.3.2 parallelism plan, §3.3.3 collectives, §3.3.4 "Reliability and Operational Challenges." Grade the claim: what accounting turns 419 unplanned interruptions into "over 90% effective training time"?

Do

Work Sasha Rush's LLM-Training-Puzzles (github.com/srush/LLM-Training-Puzzles, runs in the linked Colab): eight puzzles on training across many devices. The cluster is simulated; the reasoning is not. Take as many of the eight as the week allows, in order, and before each one write down which constraint you expect to bind, memory or communication, then check against the visualizer. The real-GPU version is the distributed-training half of CS336 Assignment 2 (Systems).

Then write the parallelism plan: one page of architecture-and-bottleneck analysis for a stated model on a stated cluster. Default case is a 70B-parameter dense transformer on 8 nodes of 8 × 80 GB GPUs, fast intra-node link, slower inter-node link, with your two bandwidths stated as assumptions. Compare two strategies (say pure ZeRO-3 data parallelism against tensor-parallel-8 within nodes × pipeline × data across them): memory per GPU, per-step communication volume on each link, which link saturates first, the plan you'd pick, and the two assumptions that would flip your answer.

Done when the analysis computes memory per GPU under both strategies (weights, gradients, optimizer states, and an activations line with its recomputation choice stated) and for each strategy names the communication link that saturates first, with the per-step byte count that says why.

Skip if you can already take a model config and a cluster spec and produce memory per GPU under two parallelism strategies with the saturating link named for each.

Take away

  • Every parallelism strategy is one move on a different tensor: shard something (optimizer states, gradients, parameters, activations, layers, experts) across devices, and pay for it with a collective on some link. Memory freed, communication owed. That is why they compose: 5D parallelism is five instances of the same trade at once.
  • Accelerator count is not delivered compute. A device count is a purchase order; a training run is that hardware times a parallelism plan, kernel efficiency, interconnect, and uptime. Both directions leak: ZeRO and FlashAttention raise what fixed hardware can train, and operational reality lowers it.
  • Llama 3's team logged 466 job interruptions across a 54-day pre-training snapshot on 16,384 GPUs, 419 of them unplanned, roughly one every three hours. Synchronous training makes any single device's failure everyone's failure.
  • Tensor parallelism communicates activations several times per layer in both directions, so it stays inside a node on the fastest link. Data parallelism communicates gradients once per step and tolerates slower links. Pipeline parallelism sends only stage-boundary activations and pays in bubbles instead.
  • The decision this bears on is whether reported accelerator access corresponds to usable training capacity. The live authority is Commerce's Bureau of Industry and Security, whose advanced-computing export controls license chips by per-device performance metrics: a rule that holds device capability fixed while the software term moves fast, outside the regime entirely.
  • When a briefing says an actor "has N accelerators," the questions that matter are interconnect, parallelism plan, utilization, and uptime. Any threshold pegged to device counts decays at the rate of systems software, which S4 takes up as a design problem.
Check yourself
  1. Mixed-precision Adam, Ψ parameters: account for the 16 bytes per parameter, then say what ZeRO-1, ZeRO-2, and ZeRO-3 each add to the sharding.
  2. Data, tensor, pipeline: what does each shard, what does each communicate, and why does tensor parallelism rarely cross a node boundary?
  3. How does FlashAttention speed up attention without approximating it, and name a run condition under which a faster attention kernel barely moves end-to-end throughput.
  4. Your job runs on 512 GPUs at a fixed global batch size and you double to 1,024. Name three mechanisms by which step time can fail to halve.

Answers. (1) 2Ψ fp16 weights + 2Ψ fp16 gradients + 12Ψ optimizer states (fp32 master weights, momentum, variance, 4Ψ each) = 16Ψ bytes. ZeRO-1 partitions the optimizer states across data-parallel ranks; ZeRO-2 adds the gradients; ZeRO-3 adds the parameters, driving per-GPU model-state memory toward 16Ψ/N at the price of modestly higher communication volume. (2) Data parallelism shards the batch, not the model, and all-reduces gradients once per step, overlappable with the backward pass and tolerant of slower links. Tensor parallelism shards weight matrices inside each layer and communicates activations several times per layer forward and backward, traffic frequent enough to need the intra-node link. Pipeline parallelism shards layers into stages and sends stage-boundary activations point-to-point: cheap communication, but it pays in bubbles that no schedule fully eliminates. 1F1B's real purchase is activation memory, since its bubble matches AFAB's. (3) It tiles Q, K, V blocks through on-chip SRAM and recomputes attention in the backward pass instead of writing and rereading the n×n matrix in HBM: same math, exact result, far fewer slow-memory accesses. If step time is dominated by inter-node gradient synchronization or pipeline bubbles, attention is a thin slice of the bill and the speedup vanishes into the binding constraint. (4) Any three of: per-GPU batch shrinks, dropping arithmetic intensity toward the memory-bound regime; collective communication cost grows with device count and rides the slowest link; synchronization means the whole step waits on stragglers; deeper pipelining adds bubble fraction; failure probability rises with N, and each interruption costs lost work since the last checkpoint plus detection-and-restart overhead.
