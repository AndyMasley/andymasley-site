Phase VIII · authored

Build an evaluation suite

Read

  • Inspect documentation (UK AI Security Institute, inspect.aisi.org.uk) — Tutorial; Components (Tasks, Datasets, Solvers, Scorers); Log Files; Sandboxing. Skip Agents and Extensions. Run the model-graded example against a small model before you read any of it.
  • ARENA Chapter 3, two sections only (learn.arena.education/chapter3_llm_evals) — [3.1] Intro to Evals, then [3.3] Running Evals with Inspect. Answer 3.1's design questions for your own W36 construct. Add [3.2] if you generate items with an LLM.
  • lm-evaluation-harness (EleutherAI, github.com/EleutherAI/lm-evaluation-harness) — optional. The README, then one task's YAML config. Find where elicitation settings live in a config-file harness.

Do

Implement the W36 spec in Inspect: 15–30 items you wrote or hand-curated, an explicit solver, and a scorer that matches the construct. Use Inspect's Docker sandbox if the construct involves tool use or code execution. Commit items, config, and the unchanged spec before the first scoring run. Run the suite twice at identical configuration and commit both logs, failed runs included. Perturb one variable (swap the grader model, or drop temperature to zero), predict the direction of the shift, rerun, and file the measured delta under validity threats. If nothing moved, say so on the card.

Then write the eval card, one to two pages, every field checkable against the logs. Construct and the decision it serves, with deviations from the W36 spec listed and dated. Population: what the items sample, and what deployment population they claim to stand in for. Task set and version. Elicitation settings per W18: temperature, truncation rule, protocol, seeds. Harness and scaffold: Inspect version, model version, sandbox. Scoring: scorer type, grader model and prompt verbatim if model-graded, plus your hand-check of grader agreement on a sample of transcripts. Uncertainty: run-to-run variance measured from your own runs, and item-sampling standard error per W10, clustered where items share a template. Validity threats: W36's table revised by implementation, perturbation delta included. Decision rule: threshold, action, and who acts.

Done when a second identical-configuration run reproduces the first within the variance the card states, and both run logs are committed beside the card.

Skip if you can already show a suite you built and reran: two identical-config committed logs, and a card whose stated variance covers the gap between them.

For the dossier, take one headline eval from the newest frontier model's vendor documentation and fill in your own card's fields; the last line lists what the documentation leaves blank. The Phase VIII gate, on the gates page, connects a score to a decision (uncertainty, threshold, authority, action) and asks why attribution is not intervention, per W39, with your card as the exhibit.

Take away

  • A score is decision-relevant only when the chain is explicit end to end: construct → items and population → elicitation → scorer → uncertainty → threshold → the action someone takes at that threshold. The card is that chain written down, so it doubles as the audit trail.
  • Your repo is not your eval. The number came from code plus a model version, a temperature and truncation rule, a grader model and prompt, and a sampling protocol. The repo pins one of the five.
  • An Inspect Task is a dataset, a solver, and a scorer bound to a configuration. The log adds what the score cannot: full config including model version and generation settings, per-sample inputs and complete message histories, token counts, and events and errors.
  • Two uncertainties, kept apart. Run-to-run spread is the pipeline's own noise, which is what the acceptance test checks. Item-sampling error is √(p(1−p)/n) per W10, and at n = 20 it swamps the first. Pinning every seed collapses run-to-run spread by construction.
  • Policy relevance: what evaluation documentation to require so third-party checking is possible. NIST's Center for AI Standards and Innovation holds pre-deployment testing agreements with five frontier labs and has completed more than 40 assessments; the UK AI Security Institute tests pre-deployment builds and maintains Inspect.
  • Such a body can verify that a documented suite reruns within its stated variance and that elicitation matches the disclosure. It cannot verify "our internal evaluations found no dangerous capability," which arrives without construct, population, settings, or logs.
Check yourself
  1. Name, in order, the links a score must connect before it is decision-relevant, and state which of them "the model scored 71%" supplies on its own.
  2. Name four things the eval log records that the headline score does not, and the check each one enables.
  3. Your 20-item suite: run one scores 70%, run two 60%, and the card claims run-to-run variance of ±3 points. Does it pass the acceptance test? Separate the two uncertainties, estimate the item-sampling one, and name one honest and one dishonest way to shrink the run-to-run gap.
  4. Your scorer is model-graded. Name the two ways the grader enters the measurement and the check that catches a grader drifting. Then: a developer says "internal evals show the capability is absent" and supplies the score. Name two checks the evaluator cannot perform, and the one-line requirement that would make both possible.

Answers. (1) Construct → items and population → elicitation settings → scorer → uncertainty → threshold → action-and-actor. "Scored 71%" supplies a point estimate and nothing else: no construct, no population, no settings, no error bar, no rule. (2) Full config including model version and generation settings, enabling reruns; per-sample inputs, outputs, and complete message histories, enabling re-grading and grader audits; token counts, enabling cost checks; events and errors, enabling forensics on failed runs. (3) Fails: the 10-point gap exceeds the stated ±3, so the card's variance claim is falsified. Fix the card or the protocol and rerun. Item-sampling SE ≈ √(0.65 × 0.35 / 20) ≈ 10.7 points, so at n = 20 the number says little about the construct's population however well the runs agree. Honest shrink: more samples per item, averaged, or more items. Dishonest: pin every seed, which verifies determinism rather than stability, or drop temperature to zero, which W18 showed changes what is being measured. (4) Through its model version and through its prompt-and-rubric; change either and the score moves, so the card records both verbatim plus measured grader-human agreement on a hand-checked sample. Drift check: re-grade a fixed archived sample whenever the grader model updates. On the developer's claim, the evaluator cannot rerun it (no config, elicitation, harness, or logs) and cannot assess construct or population. The requirement: every capability claim ships with its eval card and committed run logs.
